# 部署与运维（笔记本当服务器）

这台笔记本同时是**开发机**和**服务器**。四个 Windows 服务开机自启、崩溃自动重启，
彼此解耦于登录会话。

## 四个服务与端口

| 服务 | 端口 | 是什么 | 装在哪 |
|---|---|---|---|
| `MyPortalBackend` | 9102 | FastAPI 后台 | `backend\.venv\Scripts\python.exe` |
| `MyPortalWeb` | 5174 | **正式前端**（React/Vite 构建产物） | `node scripts/serve-static.mjs` |
| `MyPortalDemo` | 6012 | 演示站（静态） | `node scripts/serve-static.mjs` |
| `NetworkTopology` | 6010 | 画布应用（Next.js standalone） | `node server.js`（standalone 产物） |

**同源入口**：正式前端在 5174，它把 `/networktopology*` 反代到 6010 ——
所以「网络拓扑」页里的「打开画布」按钮点下去能直接开画布，**不需要用户输 URL**。

## 常用操作

```bash
# 看状态
powershell -ExecutionPolicy Bypass -File scripts/restart-all.ps1 -Status

# 重启 MyPortalWeb 与 NetworkTopology（会弹一次 UAC）
powershell -ExecutionPolicy Bypass -File scripts/restart-all.ps1

# 重启全部四个
powershell -ExecutionPolicy Bypass -File scripts/restart-services.ps1

# 装 / 卸服务
powershell -ExecutionPolicy Bypass -File scripts/install-services.ps1
powershell -ExecutionPolicy Bypass -File scripts/uninstall-services.ps1
```

**UAC 只弹一次**：`restart-all.ps1` 把两个服务的重启合在一起 ——
两次弹窗容易误点「否」。

## 改了 `serve-static.mjs` 或画布产物之后

```bash
# 1. 画布产物摆好（不需要管理员）
powershell -ExecutionPolicy Bypass -File scripts/point-nt-service.ps1 -CopyOnly

# 2. 重启服务加载新产物（需要管理员）
powershell -ExecutionPolicy Bypass -File scripts/restart-all.ps1
```

### 为什么是「复制」而不是「改服务指向」

Windows 上，进程的**当前工作目录**会锁住该目录。运行中的服务如果 cwd 是
`networktopology\.next\standalone`，那个目录就**删不掉**：

```
rm: cannot remove '.next/standalone': Device or resource busy
```

锁**阻止删除和改名，不阻止写入** —— 所以直接复制进去：

```powershell
robocopy .next-build\standalone .next\standalone /E
```

复制之后**服务的注册表项完全不用改**（AppDirectory 本来就是 `.next\standalone`），
所以「摆产物」这一步**不需要管理员**，只有「重启服务」需要。

### 画布的构建产物必须自己补两样

Next.js 的 standalone 构建**不复制**这两样，缺了就是**白屏**：

| 缺什么 | 现象 |
|---|---|
| `<standalone>/<distDir>/static` | 页面 200，但每个 `_next/static/*` 404 |
| `<standalone>/public` | `drawio/index.html` 404 → **画布一直是空的** |

`networktopology` 仓库用 `postbuild` 自动补
（`scripts/copy-standalone-assets.mjs`）。**static 的目标路径用的是 build 时
用的 distDir 名**：默认 `.next/static`，`NEXT_DIST_DIR=.next-build` 时是
`.next-build/static` —— 复制到 `.next/static` 是同一个 bug 多走一步。

**`public/` 不是「没复制」，是「被截断了」**：build 的文件追踪只带走被
import 过的文件，一个 3151 文件的 `public/`（整个 draw.io）只剩 12 个。
所以复制步骤要比较**文件数**，不能只判断「已经在那儿」。

## 船队与船舶

总览分**船队视图**与**单船视图**两级，资产清单也**先按船队-单船分类**。

| 端点 | 用途 |
|---|---|
| `GET /api/fleets` | 船队树（船队 → 船 → 统计） |
| `GET /api/fleets/overview` | 船队视图的汇总 |
| `GET /api/fleets/vessels/{id}/overview` | 单船视图的数据 |
| `GET /api/fleets/vessels` | 船列表 |
| `POST /api/fleets` · `PATCH/DELETE /api/fleets/{id}` | 船队管理 |
| `POST /api/fleets/vessels` · `PATCH/DELETE /api/fleets/vessels/{id}` | 船管理 |
| `POST /api/fleets/vessels/{id}/assets` | 批量把资产归到这艘船 |
| `GET /api/assets?vessel_id=&fleet_id=` | 资产按船/船队筛选 |

**读写认证不同**：读用宽松版（业务读接口），**写用严格版** —— 改归属是管理
动作，开发租户头不能绕过。`PATCH /api/assets` 改 `vessel_id` 同样要管理员。

**删除语义**：**删船不删资产** —— 资产变成「未归船」，还在清单里；
删船队不删船，船变成「未归队」。删的是归属关系，不是设备。

**没归船的设备不能消失**：导入进来的设备常常还不知道装在哪艘船上，
后台把它们放在「未归船」一档，总览与清单里都照样显示。

**改完后台代码要重启 `MyPortalBackend`** —— `scripts/restart-all.ps1`
已经把三个服务（后台 / 正式前端 / 画布）一起重启，只弹一次 UAC。

### 船队这一层是业务维度，不是安全维度

租户管**安全隔离**（谁能看到什么），船队管**归属**（这堆设备属于哪支船队
哪艘船）。一支船队不跨租户，一艘船也不跨租户。

事件与监控设备**没有自己的 vessel 列** —— 它们通过
`natural_id → assets.natural_id → vessel` 归属。事件量大，多一列就多一次写。

## 代理规则

`scripts/serve-static.mjs` 有一条 `/networktopology*` → 画布服务的反向代理。
**路径原样转发，不剥前缀** —— 画布的 build 用了
`NEXT_PUBLIC_BASE_PATH=/networktopology`，它自己认这个前缀，剥掉反而 404。

没有这条规则时，`/networktopology/zh` 会落到 SPA fallback，返回 myPortal
自己的 `index.html` —— **用户点「打开画布」，看到的是自己，什么也没发生**。

新起一个 service 参数：

| 参数 | 默认 | 作用 |
|---|---|---|
| `--nt` | `http://127.0.0.1:6010` | 画布服务的 origin |
| `--nt-prefix` | `/networktopology` | 同源前缀 |

## 凭据

**全部来自本地 `.env`，都不入库**：

| 变量 | 用途 |
|---|---|
| `backend/.env` → `JWT_SECRET` | 会话令牌签名 |
| `backend/.env` → `MP_ADMIN_USERNAME` / `MP_ADMIN_PASSWORD` / `MP_ADMIN_TENANT` | 种子管理员（**没有它就建不出账号**） |
| `backend/.env` → `FORTISIEM_CLIENT_ID` / `FORTISIEM_CLIENT_SECRET` | FortiSIEM **读**（OAuth client_credentials） |
| `backend/.env` → `FORTISIEM_BASIC_USER` / `FORTISIEM_BASIC_PASSWORD` | FortiSIEM **写**（Basic Auth） |

根 `.env` 与 `backend/.env` 都在 `.gitignore` 里；`.env.example` 是无秘密模板。

**读和写是两套认证**：读用 OAuth，写用 Basic Auth —— 这是 FortiSIEM 的规定，
不是实现偷懒。

## 数据

SQLite：`backend/data/myportal.db`。**WAL 模式** —— 备份要**主库 + `-wal` + `-shm`
成套复制**，恢复也要成套恢复。

`backend/data/` 整个目录不入库（含真实 SIEM 设备和事件）。

## 开发租户免登录的边界

`X-Dev-Tenant: asi` 只对**业务读接口**生效。**管理端点与 `/api/auth/me` 在任何
模式下都严格认证** —— 实测：

| 请求 | 结果 |
|---|---|
| 无 token 调 `/api/assets/cmdb/push` | 401 `需要 Bearer 令牌` |
| 错 token | 401 `令牌无效` |
| 带 `X-Dev-Tenant` 调管理端点 | 401 `需要 Bearer 令牌` |

## 已知阻塞

**FortiSIEM 的 CMDB 写权限**：

- `admin` 账号在 2026-11-22 被连续失败锁定，**连续 120 分钟未解锁** ——
  这台机器的锁定期被改过（默认 15 分钟）。
- 管理端点（用户/角色/解锁）**全 404**，OAuth 与 Basic 都够不到 ——
  **脚本无法自助解锁**，需要在 GUI 里解锁，或把
  `CMDB > Users > User Lockout > Delay next login for N minutes` 调回合理值。
- `device/discovery/add` 对 OAuth token 是 **403** —— 这是 **RBAC 细粒度**，
  不是端点不存在。解锁后若 Basic Auth 通了仍 403，需要在 GUI 的
  **Admin > Settings > Role** 给该账号授 CMDB 写权限。
